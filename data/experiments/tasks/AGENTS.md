# 任务设计

目的：找到本子类真实、常见的用户任务，把它们写成可执行、可验收的题目。

- 查公开用户需求，复用已有研究；服务商的功能菜单不能代替用户需求，帖子数量不能直接当市场频率。
- 核心交付是任务表：任务ID、用户任务、预计输入、预计输出、完成标准、未完成标准，以及必要来源。中间研究不要求单独提交报告。
- 先写最基础的完整用户任务，再增加约束或组合能力。找票任务只验找票，支付、最低价、复杂行李等需求有依据时另设题目。
- 任务说明写目标、输入与交付要求，不提前给调用命令、解题步骤或参考答案。验收条件不能新增委托、工作材料或环境授权中未告知的要求。
- 用户输入应像真实委托，保留必要材料与结果要求即可。环境限制单列；日志、证据留存和验证进程安排属于测试工作，优先由运行器和外部复核承担，不能因为便于验收就全部加入用户任务。验收可检查真实远端状态，但不应额外规定用户没有要求的实现方式。
- 任务表注明大类/子类，结果按任务归类。修改任务表述、指导程度或证据要求时另记版本；已有试跑可作为机制验证，不能静默改称自然使用体验。
- 参考Terminal-Bench/Harbor把任务说明、环境、验收分开：表格确定题目后生成prompt，验收程序由评测 Agent 单独保管。原子能力可以辅助设计，不必再维护一套独立大表。
- 在实际运行前明确判定方法；动态服务不固定未来价格答案。验收实现未完成的行标为草案，不伪装成已可测任务。

现有 `travel-flights.yaml` 是先前本地探索脚本的输入，不是正式测评。新任务先填 `travel-flights.md`；后续生成器、字段和目录按需要调整，不在这里复制研究长文。

参考已核对的固定版本：[Terminal-Bench v4.0.0 出题规范](https://github.com/harbor-framework/terminal-bench/blob/v4.0.0/rubrics/task-proposal.md)、[题目与验收一致性规范](https://github.com/harbor-framework/terminal-bench/blob/v4.0.0/rubrics/task-implementation.toml)。借鉴目标优先、结果验收与材料分离；本项目按真实需求选题，不照搬其高难度门槛或模拟服务环境。本文件约束出题工作，不能随题目传给被测Agent。

## 从任务表生成输入

- “用户任务”写成一段简短委托，把必要交付要求自然融进去；不重复追加“交付清单”。简洁不等于省略需求，也不设机械字数上限。
- “预计输入”保存原始工作材料，在新会话中作为 `input.md` 附件；不要混入评分细节、参考答案或预写调用代码。服务官方文档可以作为正常工作资料。
- “预计输出、完成标准、未完成标准”供出题与验收使用，不整列拼进 prompt。运行前逐项确认：真正的交付要求已在委托或附件中表达，评分没有新增要求，也没有漏掉用户要求。
- 测试资源范围按任务需要单列“运行资源”，与服务入口、凭据位置、预算等一起生成 `ENVIRONMENT.md`。脚本不把“只能新建空表”套到更新、搜索等其他任务上。
- 日志与 token 由运行器采集，评测 Agent 独立核验远端结果。业务本身需要的依据引用属于交付；为了评测而整理请求响应、证据索引或另起读取进程，不交给被测 Agent。
- 更新已有内容就准备真实的已有内容作为起点；创建任务不强制先写旧状态再更新。两者分别设题，改变任务或材料交付方式时升级版本，历史记录不改写。
