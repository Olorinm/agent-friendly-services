对后续金融接入建议上限为 6 次候选 API 请求；对邮箱接入保留 12 次。两个数字是小规模测试的保护建议，须在派发前结合合法免费入口和共享额度确认，不是声称完成任务必需或最多需要这些调用。执行者只做满足原委托的必要操作，不要求为用满额度增加调用。统一计数说明如下，可直接用于新 ENVIRONMENT.md：

> 候选 API 请求上限为本批明确写明的次数。对指定服务数据、身份或资源 API 的每一次已发出请求计一次，包括失败、重试及重定向产生的额外 API 请求；请求返回多少条记录不另作完成门槛。官方静态文档读取另行记录，不计入该数。总控的准备和独立核验请求单列，不占执行者上限，但同样使用服务额度。到上限后停止候选 API 操作，利用剩余模型预算交付已有结果或如实说明缺口。不得改账号、入口或出口绕过限制。

所有响应的状态由采集器保留；禁止把“发起了工具一次”当作“只发了一次 HTTP 请求”。代理、SDK 或工具内部网络请求不可见时保留计数未知，不声称保护已落实。实际服务官方限流按更严格条件执行。

邮箱仍只允许一个本轮邮箱及必要的最小匿名身份，不发信、不触发人类邮箱验证、不读既有个人邮箱。已知创建成功不重复创建；创建响应丢失或状态不明时停止并交总控核实。明确名称冲突后是否重试须事前写明，仍计入请求保护，不能借此创建额外身份。

候选 API 接入发生 403、429、明确付费要求或创建状态不确定时，不把三次重复计划当成重试许可；先停止该路径的后续派发，保留错误与具体未知原因。原因不明的 403 不解释为必须更换国家或服务器。必要的连通性诊断另行授权和记录，不混入接入成绩。

## 新验收协议应如何记录

验收逐次保留以下三项事实，不新增执行者自报日志义务，也不为方便评分增加用户交付：

1. 用户交付：原任务要求哪些已满足、缺哪些；真实结果、最终答复和可复用配置分别核对。
2. 已验证能力：实际调用或独立回执证明到哪一步；不能由最终未完成反推已验证能力不存在。
3. 限制与协议：测试保护、真实免费额度、授权、网络、执行策略或采集问题；写明证据与未知，区分候选服务错误和模型预算守卫错误。

仅有测试保护超限，不自动推导业务未完成、环境无效或服务不支持；已有用户交付按原任务核对，超限与实际费用照实保留。通过未经允许的身份、资源或替代服务完成，不能视为已在指定条件下完成。预算内没有交付则按实际缺口记录，不因为服务端已有部分结果而补写成功。

正式重复比较要求预算守卫和采集先经离线检查。若仍发生保护失效，保留该次原始记录与用户交付事实，暂停同 cohort 的后续派发；该 cohort 的严格同配置比较标为不完整。修复另开 cohort，不能只删除不利样本或追加一个成功结果来凑齐三次。先前收集的结果不消失；后续页面是否合并必须反映这一预定规则。

## 首轮交接：Grist 的同题三轮入口比较

优先级 1：比较同一现成免费账户下 REST 与官方 hosted MCP，能否稳定交付会随明细变化更新的私人共同支出账本，并比较完整交付的 Agent 开销。需求依据与独立算术方法均已写在 [原任务](collaborative-tables-shared-expenses.md)。不是跨厂商比较、接入成本复测、生产可靠性认证或压力测试。

保留 `collaborative-tables-shared-expenses-001/v1` 与六笔合成输入，不为重试改金额或放松交付。原来的单次结果不算这三轮之一。新 cohort 建议名 `grist-shared-expenses-repeat-20261010-v1`；真正的运行 ID、资源身份与派发时间由总控在执行前生成并冻结。

| 轮次 | 入口成员 | 同账户请求顺序 | 业务环境 |
| --- | --- | --- | --- |
| 1 | `grist/rest-api`、`grist/hosted-mcp` | REST 后 MCP | 两个分别确认空白的新文档；两个新执行会话 |
| 2 | `grist/rest-api`、`grist/hosted-mcp` | MCP 后 REST | 再换两个新空文档及新会话，恢复首轮准备基线 |
| 3 | `grist/rest-api`、`grist/hosted-mcp` | REST 后 MCP | 再换两个新空文档及新会话，恢复同一准备基线 |

同账号先串行执行，避免把共享限流冲突误当入口差异。三轮的先后顺序不可能完全平衡，需如实披露；不因看到首轮结果改变余下顺序。每轮两次执行全部结束、独立采集结束并封存后才派该轮两位独立验收者。只共享同轮同题的脱敏执行材料，不传别轮答案或任何验收结论。执行与验收可以跨轮调度，但复用 runtime 必须先确认结束、完成清理；不能覆盖验收尚未复制的材料。

以下为一套明确的待派发预算，不是已经运行的配置：统一 OpenCode 1.18.35 / DeepSeek V4.1 Flash (`deepseek-flash`) / high，执行每次 40 次模型请求、600 秒，验收每次 40 次、300 秒；单模型请求最大输出 32000 tokens。相较历史 25 次执行上限这是新条件，不能称仅增加重复次数。若总控选择另一已离线核验的统一预算，须在第一轮前替换本计划并冻结，不能轮间调整。

预留最后 6 次模型请求及 90 秒用于收尾：累计已发出 34 次模型请求或经过 510 秒时，取先到者，由运行器提示停止扩展工作并优先完成交付，硬上限仍为 40 次/600 秒。提示不能代填答案或在硬上限后续跑；若未完成也须如实说明。是否能实际提示、剩余预算如何提供须离线验证，不能仅凭此文档宣称已实现。此指导同时影响两入口，仍须披露，不能等同于未经提醒的日常使用。

原任务资源边界保持：每文档最多三张业务表，加默认空占位表总计不超过四张；30 条业务记录、40 次执行者服务调用；总控每文档最多 24 次独立验证调用，其中仅两次受控写入。服务 403、429 或付费要求立即停止，不换账号或入口。两入口的“服务调用”计数层次须派发前明确：REST 数据 API 操作与 MCP `tools/call` 各计一次，失败及重试也计；MCP 初始化、工具发现和传输重连另记网络开销，均计入服务实际配额。不能假定一次 MCP 调用等于其内部一次 REST 请求，也不据此比较后端 API 效率。

### 比较口径与后续优先级

逐次公开任务完成情况、明确的用户交付缺口、已验证能力、阻碍、协议偏离及实际费用。按入口列出 0–3 次实际有效完成数和逐次记录；未启动、环境无效和中止分别说明，不能补跑到三次成功才截止。三次各有独立结果，不多数票覆盖单次判定；成本均值包含已纳入条件的失败，不把未知费用当零。六次都启动不等于六次有效；对同模型、账号、上游和固定小任务的相关性如实披露，不计算普遍可用率或据三次做显著性排名。

优先级 2：用户需要更多披露接入证据时，在新金融接入协议下选定有共同覆盖和合法额度的入口；无需先重复大量业务题来修补“5条”解释。

优先级 3：AgentMail 接入路径先解决或明确连通性未知。只有两家接入路径均可合法准备且重复创建三个隔离邮箱有明确额度/授权依据时，再预定邮箱三轮；不连续重试受阻注册、不为取得结果换出口，也不把只读接入升级成收发邮件测试。

本轮已落实的是任务设计规则、限制归属、可冻结的计数说明和三轮材料交接；资源创建、运行器功能、私有新配置、模型调用、服务实测及新结论均尚未执行。
